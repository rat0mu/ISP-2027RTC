# 任務與審查

本文件提供操作與說明；協作要求以 [CONTRIBUTING.md](../CONTRIBUTING.md) 為準。

## 任務與驗收

### Issue 最少要寫什麼

| 欄位 | 應回答的問題 |
| --- | --- |
| 目的 | 為什麼需要這項工作？ |
| 範圍 | 包含哪些工作？哪些留到之後？ |
| 交付物 | 最後會提交哪些檔案、設計或結果？ |
| 驗收條件 | 由什麼證據判定已完成？ |
| 執行者 | 誰負責推進與交付？ |
| 審查人 | 誰能確認結果符合目的？ |
| 影響與依賴 | 需要哪些前置成果？會影響誰？ |

### 初期適合的任務範例

| 任務 | 交付物 | 驗收方式 |
| --- | --- | --- |
| 完善新人設定說明 | 文件更新 | 另一位成員依文件完成 clone 與 PR |
| 確認檔案放置規則 | 規則與目錄 README 更新 | 團隊能一致判斷常見檔案該放哪裡 |
| 補充介面格式 | 介面文件範例 | 能表達提供方、使用方、單位與版本 |
| 建立設計審查格式 | PR 模板更新 | 硬體與軟體任務能交代相應證據 |

Issue 是工作追蹤入口。建議用 Backlog、進行中、待審查、完成等狀態表示進度，透過 GitHub Project 或團隊選定方式管理。使用 labels 或 Project 前先由維護者建立一致名稱；目前模板沒有自動建立這些設定。


## PR 與審查

### 提交前

- 確認修改檔案均與本次任務相關。
- 排除個人路徑、認證資訊、快取與不必要產物。
- 說明測試或檢查結果；未執行就列出原因。
- 更新受影響的文件、範例與介面。
- 對圖形與二進位成果提供適當的畫面或輸出摘要。

### 審查時

審查人應確認：

1. 目的、範圍與驗收條件是否相符。
2. 是否影響其他模組、版本或操作方式。
3. 驗證方法是否足以支持所聲稱的結果。
4. 文件是否讓其他人能理解並重現。
5. 是否有需要另開任務處理的問題。

至少由一位其他成員審查。跨模組介面變更還需相關負責人確認。維護者依驗收與適用檢查結果決定是否合併。

目前已有本地文件連結 CI，見 [自動檢查](automation.md)。文件任務仍需閱讀與操作演練驗收；有實作後再加入相應建置與測試。PR 存在、編譯成功或已合併，都應與實際驗證程度分開記錄。

詳細流程見 [CONTRIBUTING.md](../CONTRIBUTING.md)。


## 各類成果的協作要求

| 類別 | 主要要求 | 建議附上的證據 |
| --- | --- | --- |
| 硬體 | 同一 PCB 指定當期編輯者；共用零件庫路徑可攜 | 原理圖／PCB 變更畫面、ERC／DRC 或尚未執行原因 |
| 韌體 | 明確對應硬體與工具鏈；分離各角色的輸出 | 建置結果、組態、邏輯測試或板級結果 |
| 地面站 | 主要入口清楚；解碼規則與協定對應 | 使用畫面、樣本資料、解析或操作測試 |
| 機構 | 保留來源 CAD 與外部引用；尺寸變更通知相關人 | 裝配畫面、接口尺寸、檢查或實測結果 |
| 文件 | 連結可用；區分現行、草案與歷史 | 另一位成員閱讀與操作結果 |
| 輔助工具 | 執行方式、輸入與輸出明確 | 可重現的命令與結果 |

### KiCad 協作提醒

.kicad_pcb 是結構化文字檔，但文字合併成功無法代替幾何與電氣檢查。同一張 PCB 的並行修改仍需要協調；不同模組原理圖也要協調頂層連接、元件編號與共用庫。

工具版本確認後寫入 hardware/README.md。升級前先討論，避免大量無關格式變更混入功能修改。

### 韌體角色提醒

主、備或其他角色的建置方式，等實際硬體確定後再規劃。若 MCU 不同，先保留各自可建置的專案。共用邏輯確定後再抽出；不同角色使用獨立輸出目錄，避免覆寫與混淆。


## 介面與設計決策

### 介面變更

介面不只包含函式，也包含：

- 電源、電平、接頭與腳位。
- 通訊欄位、封包版本、校驗與逾時。
- 資料單位、座標軸、時間基準與無效值。
- 板外形、孔位、線材空間與裝配方式。

新增或修改介面時，在 [介面規格](interfaces.md) 說明提供方、使用方、版本、影響與驗證需求，並請相關負責人確認。必要時連同雙方實作與測試一起提交。

### 重大選擇

架構、關鍵元件、工具鏈、跨模組流程等重要選擇，使用 [決策紀錄](decisions.md) 保存：

- 當時的問題與限制。
- 考慮過的方案。
- 採用的方案及理由。
- 代價、風險與影響。
- 相關 Issue、PR 與確認者。

一般文字修正保留在 PR 即可，不必每次另寫決策紀錄。
