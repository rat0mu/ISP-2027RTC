# 檔案與工程基本規則

狀態：起始規範 v0.1。工具與語言細則待有實作時補充。

## 檔案與目錄

- 以子系統或功能命名，建議英文小寫 snake_case，避免空格與 final_final 等名稱。
- 中文 Markdown 說明可放在內容中，入口採 README.md。
- 一個目錄盡量只有一個明確的現行入口；實驗與歷史版本標示狀態。
- Git 不追蹤空目錄；目前各工作目錄用 README.md 說明用途。
- 文件以 UTF-8 儲存。一般文字換行由 .gitattributes 統一；Makefile 的命令縮排保留 Tab。

## 依賴與可攜性

- 共同需要的零件庫、設定與腳本跟著來源管理。
- 使用相對路徑，避免 C:/Users/某人 或 /Users/某人 等個人路徑。
- 本機工具路徑放在被忽略的 local.mk 或對應本機設定；提供不含私密資訊的 example。
- 工具版本確認後記錄；升級工具前先確認對其他成員的影響。

## 資料與產物

- 小型測試輸入、必要校正資料與重要驗證證據可以進版控；不要全域忽略 CSV。
- 自動備份、快取、虛擬環境與中間建置輸出不進版控。
- 大型模型、二進位資產與重複壓縮包加入前先確認必要性、來源與保存方式。
- 正式製造檔與測試報告應記錄對應的來源版本。
- 不能只靠改 .gitignore 取消已追蹤檔案；清理前檢查是否仍被引用。

## 文件與介面

- 文件標示草案／現行／歷史狀態；規格待確認就明寫待確認。
- 數值標明單位與時間基準，避免依賴讀者猜測。
- 介面規格集中在 interfaces.md；變更時通知受影響模組。
- 設計與操作方式變更時，相關文件與範例一起更新。
- 重大決策用 decisions.md 留下理由與影響。

## 程式基本要求

- 命名表達用途；具有物理量的介面明確記錄單位。
- 硬體存取與可獨立測試的邏輯盡量分離。
- 錯誤與無效資料採明確表示，避免把缺資料誤當合法的 0。
- 重要錯誤保留可定位的訊息與必要上下文。
- C、Python 等詳細風格、格式化與資源限制，在選定架構後另行確認。

## 驗證回報

每次驗證至少記錄：版本、環境／組態、方法、預期、實際結果與未完成事項。自動化邏輯測試、板級測試與整機測試分別描述，不能互相替代。
