# 協作流程範例

狀態：範例說明。規則以 [CONTRIBUTING.md](../CONTRIBUTING.md) 為準；Git 指令的解釋見 [Git 工作流程](git_workflow.md)。

本文件用三個實際會遇到的任務，示範從開 Issue 到合併的每一步該寫什麼。範例中的 Issue／PR 編號（#12、#13 等）、成員 A、成員 B 都是虛構的；標示「＿」的地方要填入實際結果，不要照抄。

## 流程總覽

| 步驟 | 做什麼 | 產出 |
| --- | --- | --- |
| 1 | 開 Issue，寫清楚目的、範圍、交付物、驗收條件、執行者與審查人 | Issue 編號 |
| 2 | 從最新的 main 開任務分支 | 分支 |
| 3 | 修改、檢查、提交、推送 | commit |
| 4 | 開 PR，填模板，連到 Issue，指定審查人 | PR |
| 5 | 審查人提意見，執行者在同一分支修正 | 更新後的 PR |
| 6 | 維護者合併；同步 main 並清理分支 | main 上的成果 |

## 範例一：文件任務（最簡單，先練這個）

情境：DEC-001 寫著「433 MHz 在台灣的使用條件與比賽規則尚未確認」，成員 A 要去查清楚。

### 步驟 1：開 Issue

在 GitHub 的 Issues 分頁按 New issue，選「任務」模板，填成這樣：

```markdown
標題：確認 433 MHz 在台灣的使用條件與比賽規則

## 目的
備援遙測預定使用 433 MHz（DEC-001），但還不知道在台灣是否可合法使用、
功率上限是多少，也不知道比賽規則有沒有限制。確認前無法選定備援無線電。

## 工作範圍
- 包含：查詢主管機關的頻率使用規定、比賽規則中與無線電有關的條文。
- 暫不包含：選定無線電模組、天線設計。

## 交付物
- 更新 docs/decisions.md 的 DEC-001「代價與限制」。
- 更新 docs/interfaces.md 的 RF-002。

## 驗收條件
- [ ] 寫出可用頻率範圍與功率上限，並附上來源連結或文件名稱與頁碼。
- [ ] 寫出比賽規則的相關條文編號；規則沒有規定就明寫「未規定」。
- [ ] 查不到的項目明寫「尚未確認」與原因。

## 分工
- 執行者：成員 A
- 審查人：成員 B
- 受影響模組：硬體（備援層）、地面站

## 依賴與資料
docs/decisions.md 的 DEC-001；比賽規則文件。
```

假設建立後的編號是 #12。

### 步驟 2：開分支

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c docs/rf-433-regulation
```

分支名稱用「前綴／任務內容」。這是文件任務，所以用 `docs/`。

### 步驟 3：修改、檢查、提交

改完 `docs/decisions.md` 和 `docs/interfaces.md` 後：

```bash
python tools/check_docs.py
git status
git diff
git add docs/decisions.md docs/interfaces.md
git diff --cached
git commit -m "docs: 補上 433 MHz 的使用條件與比賽規則"
git push -u origin docs/rf-433-regulation
```

- 只 `git add` 這次任務改到的檔案，不要用 `git add .`。
- commit 訊息寫「類型: 做了什麼」。

### 步驟 4：開 PR

推送後到 GitHub 按 Compare & pull request，照模板填：

```markdown
標題：補上 433 MHz 的使用條件與比賽規則

## 目的
確認備援遙測使用 433 MHz 的法規與比賽限制。關聯 Issue：Closes #12

## 修改內容
- DEC-001「代價與限制」：把「尚未確認」改為查到的條件，附來源。
- RF-002：補上頻率範圍與功率上限。

## 驗證
- 驗證方式：python tools/check_docs.py；逐一開啟來源連結確認內容。
- 結果：文件檢查 0 個錯誤；來源連結皆可開啟。
- 尚未完成：比賽規則第 ＿ 條的解讀尚未向主辦單位確認。

## 影響
- 受影響模組：硬體（備援層）、地面站。
- 是否變更介面／資料格式／接頭／尺寸／組態：是，RF-002 新增頻率與功率限制。
- 相關文件是否同步：是。

## 自我檢查
- [x] 本 PR 的範圍清楚，已檢查提交檔案。
- [x] 已說明驗證狀態，未將未執行項目寫成通過。
- [x] 已更新受影響文件；無影響則在上方說明。
- [x] 已指定另一位成員審查。
```

- `Closes #12` 會讓 PR 合併時自動關閉 Issue #12。
- 在右側 Reviewers 選成員 B。
- 沒有電路或機構變更，最後的「硬體／機構變更時填寫」可以刪掉或寫「不適用」。

### 步驟 5：審查與修正

成員 B 在 PR 上留言，例如：

> RF-002 寫了功率上限，但沒有寫這個數字是發射功率還是等效輻射功率，請補上並註明來源頁碼。

成員 A 在同一個分支修改，再提交、推送，PR 會自動更新，不用重開：

```bash
git add docs/interfaces.md
git commit -m "docs: 註明 433 MHz 功率上限的定義與來源頁碼"
git push
```

然後在留言下回覆改了什麼。成員 B 確認後按 Approve。

### 步驟 6：合併與清理

維護者確認驗收條件都滿足後，用 squash merge 合併。之後每個人同步：

```bash
git switch main
git pull --ff-only origin main
```

確認成果在 main 上之後，刪除任務分支。

## 範例二：機構任務（有 CAD 檔）

情境：Samtec 接頭樣品到了，成員 A 要依實測尺寸更新航電艙模型。這裡只列出和範例一不同的地方。

### Issue 的重點

```markdown
標題：依 Samtec SFM／TFM 樣品實測更新 avbay 的接頭佔位與層距

## 交付物
- mechanical/cad 的新版模型與預覽圖。
- 更新 mechanical/cad/README.md 與 docs/interfaces.md 的 MECH-001。

## 驗收條件
- [ ] 附上樣品量測紀錄：插合高度、本體長寬，各量 3 次。
- [ ] 航電艙組合件干涉檢查 0 處。
- [ ] 裝入 NOSE_v1 干涉檢查 0 處，並列出最小間隙。
- [ ] MECH-001 的數字與模型一致。
```

### 分支與編輯者

```bash
git switch -c mechanical/connector-measured
```

同一個 CAD 模型同一時間只由一個人編輯。開工前在 Issue 留言「我開始改 avbay 模型」，改完推送後再留言，避免兩個人同時改造成無法合併。

### 提交

模型由腳本產生，所以腳本、模型、圖、文件要在同一個 PR 裡：

```bash
git add mechanical/cad docs/interfaces.md
git commit -m "feat: 依樣品實測更新 avbay 接頭佔位與層距"
```

### PR 的「驗證」與「硬體／機構變更」要這樣寫

```markdown
## 驗證
- 驗證方式：SOLIDWORKS 干涉檢查（組合件、裝入 NOSE_v1）；python tools/check_docs.py。
- 結果：干涉 0 處；最小徑向間隙 ＿ mm（位置：＿）；文件檢查 0 個錯誤。
- 尚未完成：未列印、未實體試裝；強度與振動未評估。

## 硬體／機構變更時填寫
- 修改區域與前後畫面：接頭佔位與層距。附上修改前後的等角視圖。
- ERC／DRC 或裝配檢查結果：CAD 干涉檢查 0 處；無電路，未執行 ERC／DRC。
- 對其他模組的影響：層距由 ＿ 改為 ＿ mm，PCB 需依新的 MECH-001 設計。
```

- CAD 檔在 GitHub 上看不出差異，一定要附圖。
- 介面（MECH-001）有變，要請硬體負責人一起確認。

## 範例三：會產生決策的任務（模擬 → 選型）

情境：要算最大加速度，決定主系統要不要加 ADXL375（DEC-002 的待確認事項）。

### 分成兩個 PR

| PR | 分支 | 內容 |
| --- | --- | --- |
| 第一個 | `experiment/max-accel-sim` | 模擬的輸入檔、設定與結果摘要 |
| 第二個 | `docs/dec-002-accel-range` | 依結果更新 DEC-002 與元件選型總表 |

先讓大家審查「模擬做得對不對」，再審查「依這個結果要怎麼決定」。兩件事混在一起，審查人很難判斷。

### 第一個 PR 的驗證欄

```markdown
## 驗證
- 驗證方式：OpenRocket（版本 ＿），馬達 ＿，起飛質量 ＿ kg。
- 結果：最大加速度 ＿ g，發生在 ＿ 秒。
- 尚未完成：質量是估計值，各組回報實際質量後要重算；未與 RocketPy 交叉比對。
```

輸入條件（馬達、質量、版本）一定要寫，別人才能重現。

### 第二個 PR 改哪些地方

- `docs/decisions.md`：DEC-002 的「代價與限制」寫入模擬結果，狀態依團隊結論改為「採用」或維持「提案中」。
- `docs/component_selection.md`：更新高 g 加速度計那一列的狀態，並在「修改紀錄」加一行。
- `docs/architecture.md`：若結論改變了架構總覽的內容，同步更新。

決策由團隊確認，不是執行者自己把狀態改成「採用」。PR 裡要寫明是誰、在哪次討論確認的。

## 寫法對照

### 分支名稱

| 不好 | 好 | 原因 |
| --- | --- | --- |
| `test` | `test/decoder-cases` | 看不出在做什麼 |
| `ming-branch` | `firmware/sensor-driver` | 以任務命名，不以人命名 |
| `final_final2` | `fix/parser-boundary` | 無法辨識目的 |

### Commit 訊息

| 不好 | 好 |
| --- | --- |
| `update` | `docs: 補充新人操作說明` |
| `改了一些東西` | `fix: 修正封包長度檢查的邊界條件` |
| `final` | `feat: 新增 MS5611 讀值驅動` |

### 驗證的寫法

| 不好 | 好 |
| --- | --- |
| 測試通過 | 在 Nucleo 板上讀取 MS5611 連續 10 分鐘，讀值在 ＿ 至 ＿ hPa 之間，無通訊錯誤 |
| 應該沒問題 | 尚未執行：手邊沒有感測器模組，預計 ＿ 補測 |
| 編譯成功所以可以用 | 建置成功（無警告）；尚未燒錄到板子上測試 |

編譯成功、板子上測過、整機測過是三件不同的事，要分開寫。

### 審查留言

| 不好 | 好 |
| --- | --- |
| 這裡怪怪的 | 第 42 行的單位寫 m，但介面規格寫的是 cm，哪個才對？ |
| LGTM（沒看內容就按同意） | 我依文件步驟實際操作一次，第 3 步的指令少了分支名稱 |
| 你應該用另一種寫法 | 建議改用查表，原因是 ＿；這不影響合併，可以另開 Issue |

## 常見情況

| 情況 | 做法 |
| --- | --- |
| 做到一半發現另一個問題 | 另開一個 Issue 記下來，不要塞進目前的 PR |
| 任務比想像中大 | 在 Issue 留言說明，拆成幾個較小的 Issue |
| 還沒做完但想讓別人先看 | 開 Draft PR |
| main 更新了，和我的分支有衝突 | 先提交自己的成果，再 `git merge origin/main`，理解兩邊目的後解決；見 [常見問題](troubleshooting.md) |
| 只改一個錯字 | 可以不開 Issue，直接開 PR，在 PR 說明寫清楚 |
| 沒有適用的測試 | 驗證欄寫「不適用」並說明原因，不要留空 |
| 審查人太久沒回 | 在 PR 留言提醒，或在例會提出；不要自己合併 |
